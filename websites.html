Case Study • Enterprise Operations

ChemOps ERP

"A mission-critical enterprise operations and manufacturing ERP engineered for specialty chemical production — featuring 8 department role-based access models, automated GST quotation workflows, batch production tracking, and atomic inventory reconciliation."

Role Full-Stack Architecture & Dev
Timeline Production Pilot
Status Live Demo
Platform Next.js 16 • Supabase PostgreSQL • Vercel
Visit Live Site View on GitHub

The Challenge

Specialty chemical manufacturers operate under rigorous regulatory compliance, complex multi-tier tax structures (HSN/GST), and zero-tolerance batch quality standards. Legacy manual record-keeping and disconnected spreadsheets created operational friction: stock double-allocation, delayed customer quotations, untracked batch stages, and lack of accountability across siloed departments (Sales, Accounts, Production, QC Lab, Warehouse, and Dispatch). The facility required a hardened, auditable operations platform enforcing strict departmental handoffs and real-time ledger consistency.

My Role & Scope

  • Architected end-to-end full-stack ERP on Next.js 16 (App Router), React 19, TypeScript, and Tailwind CSS
  • Engineered Supabase PostgreSQL data layer with cryptographic session auth and Row Level Security (RLS)
  • Designed 8 role-isolated departmental seats (Super Admin, Accounts, Sales, Production, QC Lab, Warehouse, Dispatch, Executive)
  • Engineered real-time inventory engine with atomic lot reservation, unit conversions (MT, Bags, Barrels), and automated reorder alerts
  • Built B2B quotation state machine with multi-tier HSN/GST calculation (CGST/SGST/IGST) and HOD sign-off pipelines
  • Implemented dynamic vector PDF quote and invoice generation with embedded QR codes via @react-pdf/renderer
  • Constructed batch manufacturing workflow: stage progression gating (Scheduled → Pre-Mix → Quality Check → Packaged) and variance audits
  • Built interactive end-to-end process flowmap (/flowmap) visualizing cross-department lifecycle handoffs
  • Authored complete automated verification suite (52 test files, 420 unit and integration tests passing)

Case Study • Booking Platform

The Sky Box

"The Sky Box turns an arena's QR sticker into a full booking app. Players see live slots and pay by UPI in under a minute — no app store, no sign-up — while the venue runs its entire day from one live console: orders arriving in real time, payments verified, and cancellations reopening slots instantly."

Role Product design, full-stack development, QA & launch — end to end
Timeline Oct 2026 — ~2 weeks to live production, 35 release iterations
Status Live
Platform Next.js on Vercel · installable PWA · PostgreSQL (Supabase)
Visit Live Site ↗

The Challenge

Turf slot bookings in India run on phone calls and WhatsApp. Players spam the venue with "bhai, aaj raat nu slot che?" messages, the owner answers the same question fifty times a day, and every booking lives in a chat log nobody can audit. The failure modes are constant and expensive: two groups show up for the same 7 PM slot because both were promised it verbally, players screenshot a UPI payment and claim "I've paid" for a booking that was never confirmed, and the owner has no single view of what is actually free tonight. Players have zero visibility into availability, so they either call repeatedly or simply book somewhere else.

The deeper problem was trust, not calendars. A shared spreadsheet or a form cannot tell the venue whether money actually arrived, and it cannot stop two people from holding the same slot at the same moment. So the product needed real payment verification — server-side confirmation against the payment gateway, an ownership check for counter payments, and a slot engine where the database itself makes double-booking structurally impossible, not just unlikely. Every status a player or manager sees has to be derived from server truth, never from optimistic client guesses.

The constraints shaped the architecture. Players organize games on WhatsApp and decide in seconds — they will not install an app or create an account just to book a box-cricket slot, so the whole flow had to live behind a QR scan in the browser with nothing more than a name and a phone number. The venue staff are not computer people either, so the management side had to work on a single phone kept behind the counter, protected by a short PIN, and readable at a glance from across the room. That ruled out dashboards-for-desktop-people and produced a phone-first app pair: a player booking app and a manager console, sharing one database.

My Role & Scope

  • Designed the full product end to end: design system (phone-width app canvas, frosted bars, bottom sheets, tier-coloured slot grid), every screen in both apps, and all microcopy.
  • Built the customer app: home with an auto-playing photo carousel, equal-width date chips, a colour-coded slot grid with peak/off-peak tiers and a sticky booking bar; plus My Bookings and Venue & Rules screens.
  • Built the booking engine: a slot state machine (open / held / booked / blocked / past) with 10-minute holds, transactional booking creation inside a single database transaction, and human-readable conflict errors instead of raw codes.
  • Integrated UPI payments through Cashfree with server-side order verification, webhook handling and polling — the app never trusts a client-side "I've paid" claim.
  • Built the second payment path — Pay at the counter — with an email-OTP ownership check and a manager "Verify & Confirm" step backed by UTR reference matching.
  • Built the manager console: PIN-gated login, a live day schedule that refreshes itself, payment-verification and slot-confirmation queues, bulk approve, walk-in bookings, maintenance blocking, refund requests, and a monthly calendar with revenue/occupancy analytics.
  • Implemented notifications end to end: transactional email (OTP, confirmations) and a PDF Booking Pass players can download and share, plus web push with a new-order chime for the venue.
  • Shipped it as an installable PWA: service worker, dynamic manifest, add-to-home-screen, and an offline-tolerant loading strategy with rescue UI that only appears on genuine slowness.
  • Handled the edge cases that break booking apps in the field: past-slot rejection on the server, double-hold protection, idempotent manager actions (double-tapping Approve is harmless), rate-limited OTP, and automatic release of abandoned unpaid slots.
  • Owned quality and deployment: an automated Vitest regression suite grown past 180 checks, a locked-down auth sweep of every API route, scripted live probes against production after each deploy, and a permanent canary booking that must stay untouched.

End-to-End Booking Flow

01

Scan & Land

The venue's QR poster opens the app straight on the Book tab — venue photos in an auto-playing carousel, venue branding, and equal-width date chips across the top.

02

Pick Date & Slot

The slot grid renders upcoming slots, colour-coded by availability and price tier — open, peak (amber), held, and booked. The sticky bottom bar updates the total live.

03

Hold & Details

Chosen slots are locked server-side for 10 minutes with a live countdown chip. The sheet collects name and phone, auto-applying eligible discounts before payment.

04

Pay (UPI or Counter)

Pay by UPI triggers Cashfree hosted checkout; Pay at counter triggers an email OTP for fraud-free cash settlements. Abandoned holds auto-release.

05

Confirm & Pass

Server confirms payment, generating a unique booking code, downloadable PDF pass, calendar integration, and venue directions on a single clean receipt screen.

06

Venue Live Console

The order arrives in the manager queue with audio chime and web push. Managers confirm or cancel with 1 tap, instantly syncing slots back to players.

Impact & Architecture Results

"The Sky Box went from a blank page to a live, field-tested production platform in about two weeks of October 2026, then kept hardening through 35 numbered release iterations driven by real usage — including a real customer's first booking from a phone at the venue gate. The white-label architecture is the commercial point: one venue per deployment, brand assets, photos, pricing and rules as data, so onboarding the next turf is a configuration swap, not a rebuild. Warm API responses on the booking-critical endpoints measure in the 150–250 ms range, brand assets ship inside a strict size budget with immutable caching, and a version-polling channel lets the app update itself without losing a player's place."

"The engineering that matters most is invisible. Booking creation runs inside a single database transaction that re-validates the hold and the slots together, which makes double-booking a structural impossibility rather than a race the app hopes to win. Manager actions are idempotent — approve twice and the second press is a harmless no-op — and every payment path ends in a server-side verification against the gateway, so the venue never has to trust a screenshot. Quality was enforced the same way as the features: an automated regression suite past 180 checks, a security sweep proving every admin route rejects unauthenticated calls, and an independent probe script run against the live production app after every deploy, watching a permanent canary booking that must never change."
